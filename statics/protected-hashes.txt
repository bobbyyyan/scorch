# These are SHA-256 digests of the five files as they are COMMITTED, taken from a
# clean detached checkout at 01ae768 on refactor/compiler-ir-phase3-std-move-call
# with `shasum -a 256`.  Every one of the five is byte-identical at every commit
# from origin a3b8d1e through 01ae768, so these are also the digests at the
# branch point.
#
# WHAT THE CHECK MEANS, AND WHAT IT USED TO MEAN.  The previous baseline lived
# only in evidence folders under ~/.cache/scorch-codex/ -- seventeen copies of
# it, sixteen byte-identical -- and its digests were taken from a WORKING TREE
# that carried a separate CUDA project's uncommitted edits.  Every milestone that
# reported "the five protected tracked files hash exactly as recorded" was
# therefore reporting that the working tree had not changed since that snapshot,
# not that the five tracked files were unmodified.  A clean checkout differed
# from all five recorded digests, which is how the discrepancy surfaced (review
# section 61.2).  Those past claims are true as stated about the working tree and
# are left standing; this file is where the check's meaning is written down.
#
# `statics/check_protected_files.py` runs two independent checks against these
# five paths, and the git-derived one does not read this file at all:
#
#   1. git-derived, and the one that cannot drift: the five tracked blobs at the
#      tree's HEAD equal the blobs at a reference commit.  No stored digest is
#      involved, so it stays true however this file ages.
#   2. this snapshot: the five files ON DISK match the digests below.  A clean
#      checkout at 01ae768 passes.  The live repository FAILS while the CUDA
#      project's edits are present, and that failure is the correct report --
#      it says the working tree has edits to protected files, which is a
#      different statement from "the tracked files changed".
#
